# Decisions and known limitations

This page records the decisions behind Kyumei's design, and its known
limitations.

## Dependency direction

The crates depend on each other in one direction:

```
kyumei-web (Topcoat) → kyumei-app ← kyumei-odori (Odori)
kyumei-app → kyumei-diagnostics, kyumei-evidence → kyumei-knowledge → kyumei-domain
kyumei-app, kyumei-diagnostics → kyumei-diagrams → kyumei-domain
```

The rules behind it:

- The domain knows no framework.
- Topcoat is confined to the web crate.
- Odori and the Temporal SDK are confined to the orchestration crate.
- The engine never calls outwards.

`crates/kyumei/tests/architecture.rs` enforces these rules. Two crates hold the
layers together:

- **kyumei-app** holds commands and the service port, so the web and Odori
  crates share one application layer.
- **kyumei**, the binary, assembles the other crates.

[architecture.md](architecture.md) describes every crate.

## Decisions

### Investigations are event logs

An investigation is the fold of its events, and the audit trail is derived
from the events alone. This makes several requirements straightforward:

- the trail;
- "leave and resume";
- replaying fixtures;
- showing raw evidence beside a corrected interpretation.

Corrections are events and never edits.

### Diagnosis happens in activities, never in workflow code

The durable workflow orchestrates: it serialises commands, records events and
schedules explanations. `core::handle` runs inside an activity, so the result
of each command is recorded in workflow history. Changing the knowledge pack or
the engine therefore changes future assessments, but can never make the replay
of an existing workflow non-deterministic.

### Commands are workflow updates

An update gives the web request a synchronous answer, either the events
applied or a rejection with a reason, while the workflow stays the single
writer. A busy flag serialises concurrent updates. Each command is a
submission with an id, applied once however often it is sent (see below).

### The embedded engine runs in memory, with snapshots and projections

The tokeira engine runs with `InMemory` storage and periodic snapshots. That
is simpler to ship than a database, and Kyumei is a local tool. Two safeguards
cover the gap between snapshots:

- **Projections.** A projection of each investigation's event log is written
  after every applied command. It is brought up to date whenever Kyumei reads
  a longer log from the engine: when it starts, when it shows or lists
  investigations, and before it stops. The workflow records a model
  explanation on its own, after the command that asked for it.
- **Start-up check.** Each workflow is compared with its projection when the
  engine starts.

A workflow the engine lost, or restored from an older snapshot, is restarted
from the projection. `tests/durable_golden.rs` simulates that crash.

### Engine upgrades rebuild from projections

Engine snapshots are not portable across engine releases. An engine that
can't read its snapshot reports only a failed "runtime restoration". When that
happens:

1. Kyumei keeps the file as `engine.snapshot.unreadable-<UTC time>`, never
   deleting it.
2. The engine starts empty.
3. Every investigation is restored from its projection, and the workspace
   says so.

Workflow histories do not carry over. The event log does, explanation records
included, because Kyumei brings every projection up to date before it stops.
A restored workflow asks for its model explanation again. The same path covers
a damaged snapshot, and `tests/durable_golden.rs` exercises it.

### Large content travels by reference

Evidence content over 64 KiB is put in the content-addressed blob store before
the workflow update, and the workflow carries only its SHA-256. The activity
reads the content back before running the core. Raw text over 64 KiB is also
stored by reference in the evidence record, which keeps both workflow payloads
and the event log small.

Inline, a 3 MiB screenshot would fail against the engine's 4 MiB gRPC message
limit. `tests/large_evidence.rs` covers a 3 MiB screenshot and a 1 MiB log.

### Knowledge is data, embedded at build time, and strictly validated

A binary carries the exact knowledge it was tested with. Validation rejects
these classes of mistake:

- an API field called a metric;
- an assumed `temporal_` prefix;
- a heuristic presented as Temporal behaviour;
- a verified claim without provenance;
- a label constraint on a label the metric does not have.

### Reference knowledge is generated from source

Dynamic configuration is generated by `gen-dc-claims`: in the 1.31 pack, 653
settings across the releases of the version sweep, 613 of them in 1.31.0 and
622 in 1.31.4, and in the 1.32 pack 684, each citing the line of its key in the
Temporal source. Server metrics are generated by `gen-metric-claims`: 552
definitions in the 1.31 pack, 544 of them in 1.31.0 and 547 in 1.31.4, and 611
in the 1.32 pack, each citing the line of its name. SDK metrics are generated by `gen-sdk-metric-claims` from the
Core, Go and Java sources: 61 names. Generated files are never edited. Notes
and extra provenance live in annotation files, which the loader merges into the
generated claims. A check mode, and a test when `KYUMEI_TEMPORAL_SOURCE` is
set, fail when source and file disagree.

The parser is tempdes's `config::registry_gen`, the one its `gen-dc-registry`
runs, shared rather than copied: the extractor depends on tempdes for it. The
server and Go SDK metrics generators reuse its Go lexing, which tempdes exports
for them. Core and Java get small lexers of their own, enough to skip
comments, string literals and, in Rust, `#[cfg(test)]` code.

### A server metric's labels come from review, not from its definition

Temporal attaches tags where a metric is recorded, often through a handler
built earlier with `WithTags`, so a definition has no label set to extract. The
generator therefore leaves labels empty. Annotations supply reviewed label sets,
and since the validator checks every signal's label constraints against them,
each metric a diagnostic reads must have one. 44 server metrics have one.

The same goes for a purpose (442 of the 1.31 pack's 552 definitions have no
description, and 458 of the 1.32 pack's 611) and a gauge's unit (no definition
declares one). An annotation can supply them, but never replace what the
source says. A purpose for a metric the source describes is an error, and the
judgement goes in a note instead.

### Server metric categories follow the code that records them

A metric is a Frontend, History, Matching or Worker service metric when only
that service's packages refer to it. Anything else is a `server-metric`. That
covers metrics recorded by several services, by shared code under `common/`,
`client/` or `chasm/`, and the 10 definitions nothing refers to.

The Worker service has a category of its own: 56 metrics belong only to it,
and "emitted by several services" would be false for them. Its label says
"Worker service metric", because the server's internal worker, which runs
system workflows, is not an SDK Worker.

Shared code is not traced to the services that call it, so a CHASM library
metric that only History records is still a `server-metric`. `recorded_in`
shows where it comes from. An annotation could narrow the category; none does.

### Every exposition a server's configuration allows is listed

The name and unit of a server metric on the Prometheus endpoint depend on the
metrics framework and three OpenTelemetry options. Each generated metric lists
every distinct combination, with the configuration that produces it. tally,
the default, comes first, because evidence binding prefers the first match and
records the rest as alternatives.

The rules were read from the code at the versions Temporal pins, not from
documentation:

- Temporal's handlers;
- tally v4.1.17's Prometheus reporter, which observes timers in seconds;
- the OpenTelemetry exporter v0.56.0, which appends `_milliseconds`,
  `_seconds`, `_bytes` or `_ratio`, and `_total` for counters.

The statement `server.metrics-framework` cites each source. One consequence is
that a bare timer name can be seconds (tally) or milliseconds (OpenTelemetry
with `withoutUnitSuffix`). When such evidence feeds a duration signal and the
operator has not stated a unit, Kyumei says the unit was assumed.

### One SDK metric claim covers every SDK that records the name

The Core, Go and Java SDKs share most metric names, so a claim is a name, and
each SDK that records it adds a scope entry, a provenance line and its own
expositions. An SDK joins a claim only if it records the metric. Go defines two
names it never records, and they stay Java's alone. The SDKs must agree on the
instrument, or the generator stops.

Kinds come from where a metric is recorded, not from its constant's name.
Three Java counters reach their recording call through a field and a getter
in another class. For those the generator falls back to the name's `_COUNTER`
suffix, and the claim says so.

### Java is covered through Micrometer's Prometheus registry

The Java SDK reports metrics through tally to whatever `StatsReporter` the
application configures. The SDK ships `MicrometerClientStatsReporter`, and
Micrometer's Prometheus registry decides the names:

- counters gain `_total`;
- timers become `_seconds` histograms, with buckets, because the reporter asks
  for percentile histograms;
- gauges keep their names.

The rules were read in Micrometer 1.9.9, which the SDK builds against, and
1.13.6, which its edge-dependency tests use. 1.13 moved the registry to the
Prometheus Java client 1.x, so that client's 1.2.1 source was read too. The
names come out the same in both.

Java has its own query variants, not just its own names. Its sticky polls carry
`task_queue="<queue>:sticky"`, so the Java poll and schedule-to-start queries
match `task_queue=~"<queue>(:sticky)?"`. Core counts sticky polls under the
queue's own name, so this makes the figures comparable.

Evidence requests carry a variant per SDK where the names differ. A variant can
name several families, such as Core and Go. An investigation whose SDK is known
sees only its variants; one with the SDK unknown sees every variant, labelled
with the SDKs it is for.

### The condition language uses three-valued logic

A missing fact is *unknown*, and rules fire only on *true*. Absence of evidence
cannot become evidence of absence, by construction rather than by
convention.

### A breakdown's missing label values are read as zero

Prometheus returns no series for a label value that never occurred, so an
empty result is not evidence of zero, and Kyumei never treats it as such. A
breakdown is different. When one answer to a request carries series for some
values of a label the query did not filter, the query demonstrably asked about
every value of that label. A requested signal whose value is missing from that
answer is then read as zero at the answer's sample times, with a note the
operator can correct. Without this, a cause that never occurred would stay a
candidate forever, and a diagnosis that depends on ruling it out could never
be final. The inference is limited to signals on the same metric as the
answer's own bound series, in answers to a request that expects them.

### A counter with no series reads as zero beside its witness

A failure counter that never counted has no series. The SDKs create
`long_request_failure`, with its status code, at a Worker's first failed
poll, and the server creates `service_errors_resource_exhausted`, with its
cause, at its first rejection (`sdk.long-poll-failures-counted-on-failure`,
`server.request-errors-counted-on-error`). Prometheus returns nothing for a
cluster where nothing failed, so on its own an empty result could never rule
poll throttling out, nor reach a conclusion that needs it ruled out.

Each such query has a witness: a counter the same source keeps whenever the
first could count, `long_request` beside `long_request_failure` and
`service_requests` beside `service_errors_resource_exhausted`, over the same
operation and namespace, and the same Task Queue where the query names one.
Collect now runs both. When the query returns no
series and the witness has samples in the same answer, the signal reads as
zero at the witness's sample times, and its binding and a note say so.

Without the witness, an empty result is still no evidence. No data from
Workers that aren't scraped looks exactly like no failures, which is why the
queries are not rewritten to return zero. Ten instructions, in the Workflow
Task, Activity Task, ResourceExhausted and visibility diagnostics, have
witnesses.

### Failed polls are the Task Queue's own, and a lone one is not failing

A request about a Task Queue reads its own Workers' failed polls. Core and the
Java SDK label each long poll with its Task Queue, so their queries filter on
it, and a failure on another Task Queue in the Namespace does not count
against this one. The Go SDK records long polls with its client's tags, whose
`task_queue` is `none`, so its query still covers the Namespace
(`sdk.long_request_failure`).

The Frontend closes each client connection after five minutes
(`behaviour.frontend-connection-age`), and a poll in flight on a closing
connection can fail once before the SDK retries it. That one failure makes a
one-minute rate of about 0.02 a second, above the 0.01 that counts as none.
So the rule that rules failing polls out reads their mean across the window,
not its worst minute (`heuristic.isolated-poll-failures`): polls that a rate
limit or a failing Frontend rejects fail again and again, and the mean shows
them. Many Core Workers on one Task Queue each lose a poll as they reconnect,
so their mean can still reach 0.01. The hypothesis then stays open, and the
Frontend's own count of rejected polls can rule it out.

### A query that finds nothing is recorded, and not asked again

A query that returns no series, with no witness to vouch for it, is recorded
as an observation of its own: the query and its window, bound to the signal it
informs, with no value. Rules read the signal as unknown, as before. The
request it answers counts as answered, though, because asking again would find
nothing again. Without this, an investigation whose Workers report nothing for
the Task Queue, as when none polls it, asked for the same empty answer
forever.

### Whether any Worker polls is read from Matching

When no Worker polls a Task Queue, the Workers' metrics for it have no series
at all: there is no Worker to report them. So whether any Worker polls is read
from Matching. DescribeTaskQueue lists every poller seen within
`matching.PollerHistoryTTL`, 5 minutes by default
(`behaviour.pollers-listed-for-ttl`). An empty list establishes that none
polls, and the diagnosis is final, because nothing more specific could hold. A
listed poller rules it out.

A Worker with no free slot stops polling too, so after five minutes of
exhausted slots the list is empty as well. An empty list therefore counts only
while slot exhaustion is neither supported nor established, and slots that
ran out rule absent pollers out: those Workers run, and took the queue's tasks
by polling. The Temporal CLI prints an empty list as `null`, which Kyumei
reads as empty for a field the API declares repeated. The CLI lists only the
pollers of the unversioned queue, or of the default Build ID, while
DescribeTaskQueue's default mode lists those of every loaded version.

### DescribeTaskQueue is asked for through grpcurl

Temporal CLI 1.7.0 to 1.9.1 describe a Task Queue through the Go SDK's
enhanced describe and print rows of their own (`cli.task-queue-describe`). In
that mode DescribeTaskQueue returns no effective rate limit, so no flag makes
the CLI print the limit, its source or, on 1.32, `rateLimitingActive`. The
Matching requests therefore ask first for DescribeTaskQueue in its default
mode through grpcurl, which needs no proto files because the Frontend serves
gRPC reflection (`behaviour.frontend-grpc-reflection`). Its `-emit-defaults`
keeps the zero rates, the empty poller list and the false
`rateLimitingActive` that protobuf JSON leaves out.

The CLI is the second way, for the backlog and the rates. Its JSON leaves the
rate limit and its source uninformed, so the request stays open and is asked
again. Kyumei reads the CLI's `stats` and `pollers` lists by field path, and
its ages as the CLI writes them (`2m 0.402s`, `450m s`, `3d 0h 5m 2s`). A list
whose rows describe more than one Task Queue type, as the CLI prints without
`--task-queue-type`, is left unread with a caution: summed, its rows would give
one Task Queue the other's backlog.

### Exhausted slots are read on average

A Worker polls only when it can reserve a slot, so slots that stay exhausted
establish the cause. Core counts a slot held by an outstanding poll as free
(`sdk.core-reserved-slot-counts-free`). A Worker whose slots are all busy
therefore still reports one free while the poll that follows each finished
task is in flight, and an instant sample catches it now and then. Slots count
as exhausted when fewer than one was free on average and never 5 or more
(`heuristic.slots-exhausted`). 5 or more free at every sample is headroom
(`heuristic.slots-headroom`), which rules exhaustion out.

### Reported rate limiting is read only as it is reported

On 1.32, DescribeTaskQueue's statistics say whether the rate limiter held
dispatch back within about 30 seconds before the capture, on any partition
(`rateLimitingActive`). Matching sets it only when a task and a poller, or the
forwarder that takes tasks to the parent partition, were both waiting and the
limiter kept them apart, so it never reflects Worker capacity. The 1.32
schedule-to-start diagnostics read it three ways:

- **Reported.** It supports the dispatch-limit hypothesis, and establishes it
  while Matching's backlog carries the latency and grows. That settles a limit
  which binds while dispatch runs below the limit DescribeTaskQueue reports,
  which the rates alone leave open: each read partition enforces its share,
  so with fewer write partitions than read partitions, dispatch tops out
  below the reported limit. The conclusion then says why dispatch ran below
  it. A fairness key's limit sets the flag too, so with dispatch well below
  the queue's limit, the report contests the limit's elimination rather than
  overturning it.
- **Reported false.** It only weakens the hypothesis. The classic matcher
  (`matching.useNewMatcher` off) never sets it, and a capture between bursts
  misses them.
- **Left out.** It means nothing. Protobuf JSON omits a false boolean, so a
  capture with statistics but no flag is recorded as left out of the response:
  the request is answered, and rules read the signal as unknown. The request's
  grpcurl call prints the flag when it is false. The Temporal CLI never prints
  it, and its list of rows is not read as leaving it out.

### Operator assertions count, but cannot rule anything in or out

A rule that would eliminate or establish a hypothesis is downgraded to weaken
or support when every fact it reads is an assertion. Assertions stay visible
next to measurements, so contradictions can be seen.

### A claim about a whole window needs at least three samples

A single DescribeTaskQueue capture is one sample at its capture time. It can
show that dispatch was pinned when the capture was taken, but not that
something held throughout the window.

### A comparison with before the incident is optional text

A baseline is the mean of a signal's samples from before the incident window.
Evidence often starts at the incident, as when Prometheus has kept nothing
older. So a statement that compares with a baseline puts the comparison in an
optional segment, which is left out without one, rather than printing
"unknown". The validator works out what a statement's condition ensures is
known, so a baseline the rule actually read is quoted plainly. A missing value
elsewhere still renders as "unknown", since any other statistic of a signal
with samples in the window always has a value.

### There are five states and no percentages

The states are candidate, supported, weakened, eliminated and established.
Any state can also be marked contested. A percentage would suggest a precision
the evidence does not have.

### Conclusions are ordered, and the first one that holds is the diagnosis

A conclusion is final only when no more specific conclusion could still hold.
That is why the reference investigation does not stop at step 4 with the
generic dispatch-ceiling diagnosis: the Signal-flood explanation was still
possible. A conclusion on a hypothesis that is not yet active could still hold
only if its activation still could: once records are known to be written late,
the visibility diagnostic's listing-call conclusions, which apply only while
records keep up, no longer hold back a diagnosis on the write path.

### Diagnostics are chosen by precedence, and draw their own path

When a description matches several diagnostics' symptoms, the lowest
precedence wins. More specific symptoms come first: Java Workflow thread
exhaustion before all others, Activity schedule-to-start,
history limits, Workflow Task failures and Workflow cache misses before
Workflow Task schedule-to-start, visibility before History task lag and
ResourceExhausted, and persistence latency before ResourceExhausted. A
diagnostic can recognise more than one symptom: visibility has one for stale
lists and one for failing or slow listing calls, and its diagram shows the
magnitude of the one the description matched. Each diagnostic lists the layers
its system diagram shows, with its own names for them. A Signal flood's
clients are "Signal senders"; an Activity fan-out's are "Workflows scheduling
Activities".

A stage's question can depend on earlier answers. Workflow Task timeouts are
asked about only once every failure reason is ruled out, because the retries
of a failing task also end as timeouts. When the evidence rules a question's
precondition out, the diagnostic path leaves the question off instead of
showing it as open.

### Workflow Task failures are read from the Workers' counts

The Core, Go and Java SDKs report a Workflow Task's failure to the server
only on its first attempt; later attempts are left to time out
(`sdk.wft-failure-reported-once`). History's `failed_workflow_tasks` and
`service_errors_nondeterministic` therefore rise once per Workflow and then go
flat while the Workflows stay stuck. The Workers count every failed attempt,
with its reason (`sdk.wft-failures-counted-every-attempt`), so their counter
is the one that can rule a reason out. History's counts are a fallback that
can establish a reason but never eliminate one. Whether Workflows are stuck is
read from the attempt of a stuck Workflow's pending task, because History
writes no events for retries.

### Java thread exhaustion is read from what the Worker does about it

The Java SDK's thread limit, `maxWorkflowThreadCount`, is a Worker option, and
no metric reports it, so threads in use cannot be compared with it. What a
Worker does when the pool is exhausted can be read: it evicts a cached
Workflow to free a thread and counts the eviction, which it never does while
a thread is free. That count establishes exhaustion. It leaves out Workflows
that are replaying, so threads in use held just under 600, the default limit,
establish it too. What holds the threads is read from threads in use per
cached Workflow: about one each means the cache fills the pool, several mean
the Workflows' Signal and Update handlers or branches hold them.

### Visibility asks whether records are late before choosing a path

Stale lists, missing Workflows and failing listing calls look alike from the
Web UI. Records written late explain the first two on their own, and the
store's write path decides them; listing calls that fail while records keep
up are decided by the Frontend's visibility limit, the read limit and the
store's queries. So the first question is how late History writes the records
(`task_latency_queue` for the visibility task types), and the two paths'
hypotheses activate on its answer. Until it is answered both stay open. The
store's errors are asked about on either path, before its latency, because a
store that fails writes also delays them. The visibility store's metrics have
no namespace label, so those requests cover every namespace.

### Queries match a name as tally writes it

Tally, the server's default metrics framework, writes every character of a
label value other than a letter, a digit or `_` as `_`
(`server.metrics-label-values`), and the Go SDK's tally options do the same
(`sdk.go-tally-label-values`). A namespace named `orders-prod` is therefore
`orders_prod` in those metrics, and a query for `namespace="orders-prod"`
finds nothing. The OpenTelemetry exporter keeps the value as written, and
Kyumei cannot tell from a request which one the operator runs. So a rendered
PromQL query that could be served by tally matches such a name both ways,
says so in its label, and cites the claim. Queries for Core-based and Java
Workers are left as they are. A label value in the knowledge itself, such as
the error type `serviceerror.ShardOwnershipLost`, binds evidence in either
spelling.

### Requests are chosen by a fixed, explainable order

The order is:

1. whether the request targets an unweakened hypothesis;
2. stage;
3. cost;
4. the number of hypotheses it discriminates;
5. pack order.

The investigation therefore proceeds serially along the request path. A request whose evidence a correction removed is
asked again. A request whose rendering a context change would alter is issued
again.

### The model only rewords

The deterministic explanation is always complete. A model draft replaces prose
only, and is discarded if it introduces a number, a finding or a state the
assessment does not have. The model sees the assessment and the operator's
description, never the submitted telemetry, and its output never changes the
investigation's state.

### Claude runs through Claude Code via Odori

The explainer is an Odori `AgentRun` child workflow using Odori's Claude
provider, and the provider is preflighted at start-up. Every provider, Claude
included, is given the draft's JSON schema, and the Claude provider returns
Claude Code's schema-validated `structured_output` as the reply. The guard
still validates every draft.

### An update the engine rejects as unprocessed is sent again, once applied

The engine rejects an update with `UnprocessedUpdate` when the workflow task
that carried it completed without accepting or rejecting it. Under load, while
the workflow is also running an explanation, the engine occasionally rejects
an update this way, and the rejection is not always true: the update may
already have been applied. Reading the engine suggests a race in tokeira: an
update delivered on the next workflow task can be rejected by the previous
task's completion.

So every command is a submission with an id, and a rejected one is sent again
under that id, up to three times, with a warning each time. The engine is
given the id as the update's, and the workflow remembers the replies to its
latest 64 submissions: a submission it has already applied gets its reply
back, checked once no other command is running, so a resend that waited on the
first finds its answer.

### Floats that may not be finite are written as Prometheus writes them

JSON has no NaN or infinity, and `serde_json` writes them as `null`, which can't
be read back as a number. Prometheus answers a quantile over a step without
traffic with NaN, so evidence is full of it. Series points, scalar values and
the values findings rest on are written as `"NaN"`, `"+Inf"` or `"-Inf"` when
they aren't finite, and `null` reads back as NaN. Values typed into **Enter
values** must be finite.

### A view query that times out is sent again

An investigation is read with a workflow query, which changes nothing, so a
query can be sent again at no risk. Under load, the engine can leave a query
unanswered until the client's default 30-second deadline. Each query waits at
most 10 seconds and is sent up to three times when it times out or the engine
is unavailable, with a warning each time. Only an engine that reports the
workflow missing makes the investigation "not found"; any other failure is
reported as it is.

### Kyumei uses Odori 0.3

Kyumei runs on Odori 0.3.0, which embeds tokeira 0.6.1 and the Temporal Rust
SDK 1.0. In a soak of 200 runs of `tests/durable_golden.rs`, two at a time,
every run passes; one command is rejected as unprocessed, sent again and
applied once.

### Topcoat is server-rendered

Every page is HTML from the server, and every action is a form post.
Everything works without JavaScript. A small script adds conveniences:

- copy buttons on queries;
- opening the section that holds a linked observation;
- refreshing the page when the investigation changes elsewhere. If the
  operator has unsaved input, it shows a banner instead of reloading. The
  notice about evidence just received survives the refresh, since the change
  is often the explanation of that same evidence;
- applying the time zone as soon as it is chosen (without the script, a
  **Set** button does it).

Kyumei runs on Topcoat 0.10.0, with route parameters declared in handler paths
and read with `path_param!`. It uses no browser runtime expressions, nor
Topcoat's client-side navigation and prefetching.

### The version sweep checks every patch release, and claims say which

The 1.31 pack's generators run against all 32 three-part releases from 1.27.0
to 1.31.4, not one per minor version, because patch releases do change
settings: 1.30 gained eleven settings across its patches, 1.30.2 changed a
default that 1.31.0 changed back, and 1.30.7 and 1.31.3 added the same four. A claim lists the releases where it is the same, so an
operator on 1.29.3 sees exactly which settings and metrics were checked for
1.29.3.

- **Hotfix tags are left out.** Four-part tags such as v1.29.4.1 are not
  semantic versions, and Kyumei's server version has three parts.
- **A pack from 1.31 on, not before.** Each minor release from 1.31 has a pack
  of its own, read at that release: 1.31 and 1.32. Before 1.31 the diagnostics
  and most behaviours were never read, so a pack per older minor version would
  have settings and metrics but nothing to diagnose with. Older releases use
  the 1.31 pack, which says what was checked for them.
- **Hand-written knowledge follows its sources.** A behaviour read at 1.31.0
  extends to another release only where every file it cites is byte-identical,
  or where someone read the change. Matching excerpts would show that a line
  still exists, not that the behaviour around it is unchanged. Most behaviours
  therefore hold for 1.31.0 to 1.31.4, and a few back to 1.29 or 1.30.
- **Reviewed labels narrow a metric.** An annotation's labels, purpose or unit
  were reviewed for particular releases, so the metric is verified only for
  those, though its name is checked in more. A claim marked verified has
  everything it states verified.
- **The metrics prefix has its own statement.** 1.27's OpenTelemetry framework
  never applies `global.metrics.prefix`; 1.28 added that, so
  `server.metrics-prefix` holds from 1.28.0.

### Behaviour is read from source, and run when it contradicts the pack

Limit and behaviour statements are written by reading the code at the pinned
release, one diagnostic area at a time. Each sentence rests on the lines it
cites. When the code describes itself one way and does another, the statement
follows what the code does.

When a reading contradicts a statement already in the pack, the code is also
run before the statement changes. `limit.dispatch-applied-on-change` rests on
such a run: Matching computes a partition's default dispatch limit but applies
it only when the effective rate changes. A probe test against the v1.31.0
source shows it: a partition built with default configuration dispatches 5,000
tasks in one instant, and is limited to 1,000 tasks/s only after a Worker rate
is set and removed. The reference investigation is unaffected, because its
evidence shows dispatch pinned at the limit.

### The companion is two crates

Kyumei's evidence interpreter must read sample blocks, and the architecture
test keeps tokio, HTTP clients and frameworks out of the core crates. So the
format is `kyumei-samples`: the armour, the payload, its encodings and request
codes, with no framework and no other Kyumei crate. `kyumei-evidence` reads
blocks with it. The client and binary are `kyumei-collect`, built on
`kyumei-samples` and nothing else of Kyumei's, so the companion carries no
knowledge, model or agent code. The architecture test enforces both.

### Simulation comes from tempdes, through one crate

Kyumei's rules say which way the evidence points, not whether a cause is big
enough to explain what the operator sees. [tempdes](https://github.com/iw/tempdes)
simulates a Temporal Server 1.31.0 cluster request by request, so Kyumei uses
it as a dependency pinned to a commit, never as a copy. A simulated result can
then cite exactly what produced it, and the simulator's model keeps one home.
`kyumei-sim` is the only crate that runs tempdes, and `kyumei-app` the only one
that uses it.

A run advances in slices, and its metrics are scraped every 15 simulated
seconds. Queries are answered over the scrapes with the PromQL Kyumei's
requests use, evaluated as Prometheus evaluates it:

- matchers are anchored regular expressions or exact values;
- `rate` and `increase` count a drop as a restart and extrapolate to their
  range's edges;
- `histogram_quantile` interpolates within the bucket the quantile falls in;
- aggregations drop the metric name.

Every PromQL query in the pack parses, and anything else is refused rather
than approximated. The answers are the sample blocks Collect now records, so
simulated evidence travels as collected evidence does. tempdes keeps its
scheduler in thread-local state, which a new run resets; every run still has a
thread of its own, so that a failing run stops alone. A run stops at a budget
of real time, checked between scrapes. The same seed gives the same scrapes.

`crates/kyumei-app/tests/incidents.rs` works simulated incidents through the
Workflow Task diagnostic, each with one cause, as an operator with Collect now
works one:

- PromQL requests are answered from the scrapes;
- the Matching queue request is answered with a DescribeTaskQueue capture
  taken from them near the end of the window;
- the partition request is answered with the scenario's dynamic configuration.

Slots that never free, throttled polls, a dispatch ceiling, starved pollers, a
Signal flood against a dispatch ceiling, no pollers at all, and Workflow Tasks
reaching Matching late are each diagnosed as their cause, every request
answered once. Each run simulates 30 minutes in a few seconds. Write and read
partitions that differ have no incident: tempdes clamps them rather than
simulating them.

### A simulation asks whether a cause is big enough

The rules say which way the evidence points. A simulation says whether a
cause, at the size the evidence shows, could produce the symptom. A diagnostic
declares its simulations in its knowledge: the hypothesis each tests, the
scenario it builds, the observed facts that calibrate it, and the signal its
result informs. For the Workflow Task diagnostic, `dispatch-ceiling-size` runs
the Task Queue with its observed add rate against its observed dispatch limit
and partitions, with nothing else in the way, over the incident window, and
reports the schedule-to-start that gives.

- **When.** A simulation is due once its calibration inputs are observed facts
  and the symptom it is compared with is known, as an observed fact or the
  operator's word. It runs once for those inputs, never for an eliminated
  hypothesis, and only for a self-hosted server of the release tempdes models,
  1.31.
- **Scaled.** The wait a rate limit causes depends on how far adds exceed it
  and for how long, so the run divides both rates by the same factor, to stay
  near 100 tasks a second, and says so.
- **Recorded as evidence.** A run is evidence of its own: its origin names
  tempdes, its commit and the seed (always 1), its body is the scenario as
  run, and a record keeps the inputs, the evidence they came from, the scale
  and the results. Its notes give the fit, the simulated latency against the
  observed. A run that fails is recorded with why, so it isn't tried again.
- **Simulated facts.** The run's result is a simulated fact, a standing of its
  own beside observed facts and operator assertions. Like an assertion it can
  support or weaken a hypothesis, never establish or eliminate one: the
  validator refuses a rule that would, and the engine downgrades any that
  reads a simulated fact. `heuristic.simulation-reproduces` decides what
  counts: within half to twice the observed latency supports the cause, below
  a fifth weakens it, and anything else gets no say.
- **In an activity.** On Odori a run is an activity, so its result is in the
  workflow's history. `kyumei serve` runs simulations unless
  `--no-simulate` is given.

The reference investigation's ceiling simulates to 40.6 s against the 30 s the
operator reported, 1.35×, so the simulation supports the ceiling it already
established.

### Samples are exact unless rounding is asked for

A block keeps every value bit for bit, NaN and the infinities included, and
every timestamp to the millisecond. Each series is written in whichever of
four exact encodings is smallest (whole numbers, decimals with a common
exponent, decimals with a steady exponent, or XORed float bits), then the
payload is deflated. Noisy measurements cost about 3 bytes a sample;
counts and flat series much less. Rounding to N significant digits is
opt-in (`--round N`): it saves about a third of the lines at 3 digits, but a
rounded value can move a threshold comparison, so the block records it and
Kyumei notes it on the evidence.

### A damaged block is refused whole

The last line of a block states the payload's length and the CRC-32 of its
compressed bytes. A block that lost a line, gained text or had a character
changed in copying is refused with the reason, rather than read in part:
a series missing its last minutes could pass for a recovery.

### Blocks say which request they answer

A request code carries the investigation, the request, the queries and the
window; the block repeats the investigation and the request. Pasted into
another request, the block is still read, since its samples are still
observed telemetry and binding decides what they inform, but Kyumei says
that it was collected for another request.

### Pasted blocks are the operator's evidence; Collect now is Kyumei's

A pasted or uploaded block keeps the operator's origin, and its notes name
the collector, its source and when it ran. Evidence from Collect now has the
origin `Collector kyumei`. Both are observed telemetry. The raw evidence is
the block either way, so it is exported and replayed like any other.

### Collect now runs only the request's own queries

Collect now takes no query from the form. It runs the queries Kyumei
rendered for the open request, over the request's window. Values from the
investigation's context are escaped for where they stand: as a regex literal
inside a regex matcher, as a string literal inside any other string. A
namespace or Task Queue name therefore cannot change what a query reads,
including with Kyumei's credentials. A query that still has a placeholder is
not run; adding the value under Edit context issues the request again with
it filled in.

### Commands quote a name only where the shell would misread it

Kyumei fills the namespace and Task Queue into the Temporal CLI commands and
grpcurl calls the operator copies, quoted as bash and zsh read them. A name
with a space, a quote or a `$` therefore reaches the program as written,
rather than splitting into several arguments or expanding into something
else. A name made only of letters, digits and `-_.,:/@%+` stands as it is, so
the usual names read as they are typed. Any other is single-quoted, since
inside single quotes neither shell expands anything, `!` included; a `'` in
the name closes the quotes, follows escaped and reopens them. `=` and `~` are
quoted too: at the start of a word, zsh reads `=name` as a command's path and
both shells read `~` as a home directory. grpcurl's request is JSON inside
single quotes, so a name in it is escaped as a JSON string and then for those
quotes. The quoting is for bash, zsh and other POSIX shells; fish reads a
backslash inside single quotes as an escape.

### An encoded file's window is the file's

`kyumei-collect encode` turns saved query output into a block. Its window is
the range the files cover, unless one is given, not the request code's:
saved output may cover more or less than the request asked for.

### Operations material is cited, never bundled

tsurdilo/temporal-server-operations has no licence. Kyumei therefore links to
its runbooks, playbooks and dashboards at a pinned commit, and reads the
operator's own copy of the dashboards, given with `--dashboards` or uploaded. It
bundles none of their text or JSON: a reference quotes only the title and
heading it cites, and says in Kyumei's words why it applies. The tests that
need the real dashboards run only when a checkout is given
(`KYUMEI_OPERATIONS_SOURCE`); the others use dashboards written for them.

### References are knowledge, checked at their commit

A reference is data in the pack, like a claim, and is checked the same way:
loading refuses one that cites an unpinned source or links what no diagnostic
defines, and `kyumei knowledge verify` checks every title, section anchor and
panel id in a checkout at the pinned commit. What a reference links comes from
reading its document, not from its file name.

### A chart is drawn as the panel that shows the same quantity

A panel is a candidate when one of its queries reads the evidence's metric
alone, as a quantile when the evidence is one, through filters that keep at
least one of the series. Matching by name alone would draw raw error rates on a
success-ratio panel, and Java thread counts on the Go dashboard's goroutine
panel. When the investigation does not say which SDK the Workers use, the
evidence's own series names often do: `…_total` counters are Java's. Among the
candidates, the panel the request references comes first, then one on the SDK's
dashboard, then one that groups by the series' labels; ties go to the dashboard
loaded first. Groups of series that choose the same panel are drawn together, as
the panel draws its queries together.

### A label that carries another's value fills the legend

History keeps `operation` beside `task_type` on its task metrics, with the same
value. The operations dashboards group by `operation`, Kyumei's requests by
`task_type`. The knowledge records the pair (`same_as`), so a panel's
`{{operation}}` legend is filled from `task_type`, and the chart says so.

### Thresholds outside the evidence are listed, not drawn

A panel's thresholds are drawn in its unit. One far outside the evidence's
range would squash the series against an axis; it is listed under the chart
instead. Percentage thresholds depend on the panel's range in Grafana and are
not drawn.

### Cross-checks run both ways

`kyumei dashboards check` and the Dashboards page check every panel against
the knowledge: the metric names, labels and units it reads, and thresholds
that disagree with other dashboards' for the same metric. The command checks
against every pack, since a metric one release adds is unknown to the packs
before it; the page checks against one at a time, the newest unless another
is chosen. A finding can be the
knowledge's fault as much as the dashboard's, so it is read against the source
before either is changed. At `5a71c36` the operations dashboards have three:

- the Go SDK dashboard's latency thresholds are a thousandfold the Core and
  Java dashboards' (1000 s where they have 1 s);
- two Core dashboard panels' are a thousandfold smaller (5 ms where the others
  have 5 s);
- the poll empty panels group by `workflow_type`, which no SDK records on empty
  polls.

### Linked panels open in Kyumei, with live data

The panels the knowledge links to open as pages in Kyumei, drawn from the same
endpoint as Collect now, rather than sending the operator to Grafana or to the
dashboard's JSON. Seeing the metric where the diagnosis is, in the panel's
own terms, is the point; whole dashboards stay in Grafana. The application
layer plans the reading and draws it; only the interface reaches the network,
as for Collect now. A panel's reading becomes evidence only when the operator
adds it, and then exactly as Collect now's does, citing the panel.

### Times are UTC, shown in the operator's zone

Kyumei stores and reasons in UTC. A cookie keeps each browser's zone, and
every page, chart and export is built in it; forms read typed times in it, and
their labels name it. Zones are named by IANA name and shown with the
abbreviation the time zone database gives, falling back to the offset when it
gives only a number. Abbreviations are only ever written, never read, since
several zones share one (IST, CST). The text Kyumei writes (request windows,
notes, explanations, a model's wording) carries UTC times in a few fixed forms,
which presentation rewrites into the zone; the operator's own words and
evidence as submitted are never touched. The time zone database is bundled, so
labels don't depend on the machine.

### The configuration and the data live where the platform keeps them

The configuration file is `kyumei/config.toml` in the platform's configuration
directory, and the data directory is `kyumei` in its local data directory
(`~/.config` and `~/.local/share` on Linux, `~/Library/Application Support` on
macOS, `%APPDATA%` and `%LOCALAPPDATA%` on Windows). The configuration is
checked when Kyumei starts, and a mistake stops it.

### Profiles fill the form; the operator asserts what is submitted

An environment profile fills a new investigation's context, which stays
editable, and the investigation records the profile's name. What is submitted
is the operator's assertion, as typed values are. Profiles don't choose a
metrics endpoint: Collect now and linked panels read one endpoint per Kyumei.

### A new investigation starts with the last hour

The form's incident window starts as the hour up to now, since most
investigations start during the incident. It is a default in the form, not a
guess Kyumei makes: the operator sees it, changes or clears it, and what is
submitted is theirs. Investigations opened by other means (fixtures, the API)
leave an unknown window unknown.

### A dashboard's version is its title's

The operations repository has no tags or releases. A dashboard's version is
cited from its title, which is part of the dashboard, not from its README's
"Current version" line, which can lag: at `5a71c36` the Task Queue Partitions
README says v1.1.0 while the dashboard says v1.4.0. A playbook cites the
dashboard version the playbooks index says it needs. Each version is checked
on its line at the pin, like a claim's excerpt.

### Knowledge updates are read, never applied

`kyumei knowledge updates` reports what is newer upstream and changes nothing.
Pins move only by a reviewed change to the sources, verified like any other.

## Known limitations

### Scope

- **Twelve diagnostics, verified for 1.31 and 1.32.** The diagnostics are
  Workflow Task schedule-to-start, Activity schedule-to-start, History's
  persistence latency, ResourceExhausted rejections, Workflow Task failures,
  history limits, Workflow cache misses, History task lag, History's Workflow
  cache, shard ownership churn, visibility lag and errors, and Java Workflow
  thread exhaustion. The packs are verified for 1.31.0 to 1.31.4 and for
  1.32.0 and 1.32.1. For 1.27.0 to 1.30.8, the settings' and metrics' names,
  types and defaults are checked, but most behaviours, the reviewed labels of
  the metrics the diagnostics read, and the DescribeTaskQueue fields are
  verified for 1.31 only. Releases before 1.27.0 get the 1.31 pack, and
  releases after 1.32 the 1.32 pack, with every claim unverified for them; a
  hotfix tag gets its minor release's pack, unverified the same way.
- **What the diagnostics leave out.**
  - ResourceExhausted covers the Frontend's namespace and host rate limits,
    its cap on long-running requests, and persistence limits.
    BusyWorkflow, SystemOverloaded, ApsLimit and the other causes are
    recognised in evidence but not diagnosed.
  - Persistence latency reads History's pool for its main SQL datastore.
    Only MySQL and PostgreSQL report the pool, so with Cassandra or SQLite
    the pool stage stays open; visibility stores are covered by visibility
    lag and errors.
  - The Activity fan-out signal counts ScheduleActivityTask commands across
    the namespace, so it can show that a fan-out is large enough to explain
    a Task Queue's add rate, not that every Activity went to that Task Queue.
  - Workflow Task failures covers the reasons the Workers count:
    nondeterminism, errors in Workflow code, and completions too large to
    send, then timeouts. Failures History finds itself when a task completes,
    such as invalid command attributes, are not diagnosed. Without the
    Workers' metrics, a reason can be established but not ruled out. The
    attempt histogram covers every Workflow in the namespace.
  - History limits reads one affected Workflow and compares it with the
    default limits and continue-as-new thresholds; only its termination
    reason establishes which limit applied. The server's history size
    histogram stops at 16 MiB, below the 50 MiB limit, so it is not used.
  - Workflow cache misses judges a full cache by its size holding at its
    peak, since the SDKs count evictions differently and Java not at all for
    a full cache. The counts of completions with and without sticky
    execution cover the whole cluster.
  - History task lag reads the task metrics of the affected namespace and
    the worst task type; it does not split timer, transfer and visibility
    queues, and it leaves the task-scheduler rate limiter, off by default,
    and the history task DLQ out.
  - History's Workflow cache reads the fullest host's cache, and its gauges
    are shared with replication's progress cache under the same cache type.
    A cache sized in bytes (history.cacheSizeBasedLimit) is not covered.
  - Shard ownership churn reads ShardOwnershipLost at the Frontend, not the
    "shard status unknown" errors of a shard still being taken, and cannot
    tell a planned restart from a crash: both change membership.
  - Visibility lag and errors reads the visibility store's metrics for every
    namespace together, since they have no namespace label. While records are
    written late it does not ask about listing calls. It leaves out a
    secondary (dual) visibility store, the Frontend's host-level limit on
    visibility calls, Elasticsearch's delay between acknowledging a write and
    showing it in searches, and archival.
  - Java Workflow thread exhaustion cannot read the configured thread limit,
    which no metric reports: it establishes an exhausted pool from evictions
    to free a thread, or from threads in use held at the default 600. The
    eviction count leaves out Workflows that are replaying. Threads per cached
    Workflow compare the busiest Worker's peaks, which can come from
    different Workers. Virtual Workflow threads are not covered.
- **SDK coverage.** SDK metrics are generated from Core at `acac9e3f`
  (cross-checked against Python 1.25.0), Go v1.44.0 and Java v1.40.0. Their
  Prometheus names are verified for:
  - Core's own Prometheus exporter;
  - Go's tally and OpenTelemetry handlers;
  - Java's Micrometer Prometheus registry.

  Core's OTLP exporter, Java's other registries and tally reporters, and the
  .NET, Ruby and TypeScript wrappers' own options are not covered. Their names
  in Prometheus can differ.
- **The Temporal CLI describes one version, without the rate limit.**
  `temporal task-queue describe` is verified against CLI 1.7.0 to 1.9.1. It
  covers only the unversioned queue, or the default Build ID's, and Kyumei
  cannot tell from its output whether the Workers are versioned: with Worker
  Deployment Versions its backlog and pollers can fall short. Its JSON never
  informs the rate limit or its source. The requests ask for grpcurl first,
  whose DescribeTaskQueue merges every version.
- **Most metrics are names and types only.** Kyumei recognises evidence for
  any of a pack's server metrics (552 in the 1.31 pack, 611 in the 1.32 pack)
  and 61 SDK metrics by name. Only the 44 server
  and 15 SDK metrics the diagnostics read have reviewed labels. 442 server
  metrics in the 1.31 pack, 458 in the 1.32 pack and 20 SDK metrics have no
  description in their source.
- **Some exported names are not modelled.** Matching's priority and fairness
  matchers record many metrics a second time under a `pri_` or `fair_` prefix
  (`service/matching/pri_metrics_handler.go`). A configured
  `global.metrics.prefix` changes every name. Neither appears in the
  expositions, so such series are not recognised. The statsd reporter is not
  covered.
- **Screenshots are kept but not read.** No OCR is done.

### Behaviour

- **Choosing a symptom after opening does not re-read the description.** If
  the description matched no symptom, quantities in it ("about 30 seconds")
  are not extracted once a symptom is chosen later. Enter them as values
  instead.
- **One capture can't rule out a dispatch ceiling.** Ruling a ceiling out takes
  three samples of the dispatch rate, and the Matching queue request asks for
  one DescribeTaskQueue capture. Poller starvation and late arrival at
  Matching are therefore reached but not final unless more captures are
  added.
- **Only the dispatch ceiling is simulated.** The other Workflow Task causes
  have no simulation yet, and none of the other diagnostics has one. A
  simulation needs the partition count and an incident window with an end.
- **Most failure counters have no witness yet.** Persistence errors, Workflow
  Task failures and sticky cache misses are created at their first increment
  too, but their requests have no witness, so an empty result is no evidence.
- **One open request at a time.** This is by design. Evidence submitted from
  the workspace is recorded as an answer to the open request. Kyumei still binds
  anything it recognises, such as another metric, to the signal it informs.
  Content it cannot recognise is bound to the open request's signal only when
  that request expects exactly one signal, and the binding says so.

### Dashboards

- **Only time series panels are drawn.** Stat, gauge and table panels are read
  but not drawn, and their queries are not cross-checked.
- **Variables beyond the namespace, the quantile and the rate interval are not
  filled in evidence charts.** A legend that uses another variable keeps it as
  written. On a linked panel's page, the Task Queue also comes from the
  investigation, a custom variable from its options, and any other variable
  is typed: Kyumei doesn't list a query variable's values from Prometheus.
- **Panels are found by the metrics Kyumei knows.** Evidence whose series bind
  to no claim is drawn only by a panel reading the same exposed name.
- **Grafana links assume the same uid.** The link to a panel uses the
  dashboard's uid, so it opens the panel only in a Grafana that imported the
  dashboard without changing it.
- **The Java OpenTelemetry dashboard has no references.** Kyumei's Java
  knowledge follows Micrometer's Prometheus registry, so panels are linked for
  that dashboard only.

### Time zones

- **Kyumei's text is rewritten by its forms.** Times in the forms Kyumei
  writes them (`2026-10-14 13:21 UTC`, `13:03 UTC`, windows) are shown in the
  chosen zone. A model's wording in another form, such as an ISO timestamp, is
  shown as written. A time without a date is taken to be on the incident's
  first day.

### Knowledge updates

- **Changed files come from GitHub.** Tags and heads come from any Git host,
  but the commit count and changed files only from GitHub's compare API, which
  lists at most 300 files.

### Collecting metrics

- **Collect now waits for its queries.** It runs in the form post, one query
  after another, each with a 60-second timeout. A slow endpoint keeps the
  page waiting.
- **Only PromQL range queries are collected.** CLI output, DescribeTaskQueue
  responses and dynamic configuration are pasted.
- **Pseudonyms cannot be compared.** A redacted label's values are
  pseudonyms in Kyumei: they cannot be matched with the investigation's
  namespace or Task Queue, nor with values the knowledge names. Redact
  identifying labels such as `namespace` and `task_queue`, not ones a signal
  is defined by, such as `worker_type` or `operation`.
- **Anyone who can reach Kyumei can use Collect now.** Kyumei has no
  authentication. With an endpoint configured, anyone who can open the
  workspace can have it run its requests' queries with the endpoint's
  credentials.

### Durability and scale

- **Every activity receives the whole event log.** The reference investigation's
  complete log is about 70 KB. With 64 KiB inline limits, an investigation
  would need hundreds of large submissions to approach the engine's 4 MiB
  message limit. The limit has not been tested beyond that.
- **Busy machines see occasional 10-second pauses.** In soaks with several
  engines busy in one process, a few runs of the durable tests take about 10 s
  longer than usual. That is consistent with a workflow task waiting out its
  10-second timeout before the engine retries it. Those runs still complete;
  the reference test allows 60 s for its explanation for this reason.
- **Explanations are regenerated after recovery.** If a workflow is restored
  from its projection after a crash or an engine upgrade, the model
  explanation for the latest assessment is requested again. The deterministic
  explanation is always present.
- **Single user, no authentication.** Run Kyumei where only people you trust
  can reach it, or behind a proxy that authenticates them.

## Live model explainers

The explainer path is tested end to end with a scripted agent in
`tests/durable_golden.rs`. That test runs a real Odori `AgentRun` child
workflow and validates the draft. `tests/live_claude.rs` runs the same path
with a real model. It is `#[ignore]`d, since it spends a model turn, and uses
Claude Code unless `KYUMEI_LIVE_EXPLAINER=codex` chooses the Codex CLI; either
must be logged in:

```bash
cargo test -p kyumei-odori --test live_claude -- --ignored
```

When a provider fails, Kyumei falls back to the deterministic explanation and
shows the cause in the workspace.
